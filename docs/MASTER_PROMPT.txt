You are working on a project called ALTiLINK.

ALTiLINK is a hiking/group-awareness and emergency-safety system designed for groups trekking in areas where normal cellular connectivity may be unreliable.

The project has TWO connected parts:

1. SOFTWARE PLATFORM
   - React + TypeScript web application
   - Python backend
   - Existing machine-learning fall detection model
   - Maps, group awareness, checkpoints, backtracking, emergency/SOS workflows
   - Communication simulation and synchronization

2. HARDWARE PLATFORM
   - Heltec WiFi LoRa 32 V3 boards
   - LoRa communication
   - NEO-6M GPS module
   - Future IMU/sensor hardware
   - Hardware-generated location and emergency data
   - Hardware communication with the ALTiLINK application

IMPORTANT:
The software prototype already exists and is substantially implemented.
Hardware integration is currently being developed separately.
Do NOT pretend that hardware communication is already integrated into the web application unless the code explicitly shows that it is.

==================================================
1. FINAL PURPOSE OF ALTiLINK
==================================================

The final ALTiLINK system should provide a safety and group-awareness platform for hikers.

A group of trekkers should be able to:

- Create or join a hiking group
- Select a predefined trail
- Start and end a hike
- See group members and their locations
- Track GPS positions
- Define/check communication limits
- Automatically create trail checkpoints
- Delete incorrect/unwanted checkpoints
- Generate a reverse/backtracking route
- Trigger emergency SOS
- Detect a possible fall using the existing ML model
- Give the user a short opportunity to cancel a false fall alert
- Automatically send an emergency alert if the user does not cancel
- Share emergency information with the rest of the group
- Eventually use LoRa hardware for communication when cellular connectivity is unavailable

The system should remain HUMAN-CENTERED and PRACTICAL.

Do NOT turn the UI into a futuristic/cyberpunk interface.

Do NOT add unnecessary technical jargon to the normal user-facing UI.

The system should look like a realistic hiking safety application.

--------------------------------------------------
5.7 HOW AUTOMATIC CHECKPOINT CREATION WORKS
--------------------------------------------------

SimulationContext.tsx contains:

advanceSimulatedTime()

Conceptually:

oldElapsed = simulatedElapsedSeconds

newElapsed =
    oldElapsed + minutes * 60

intervalSec =
    checkpointIntervalMinutes * 60

The code checks whether the simulated time crossed a checkpoint interval.

When an interval is crossed, a checkpoint is created.

Checkpoint information includes things such as:

- ID
- name
- latitude
- longitude
- altitude
- sequence number
- timestamp
- passed state

The checkpoint is then stored in application state and displayed on the map.

This is currently a SIMULATION.

It is NOT yet driven by real GPS hardware.

==================================================

Backtracking utility:

The function:

3. Reverses the order

9. LINK QUALITY / COMMUNICATION RANGE
==================================================

Utility:

src/utils/linkAssessment.ts

The current link-quality system is a simulation.

It contains terrain-specific predefined measurements.

Example Dense Forest values include approximately:

100 m:
RSSI -65
SNR 9
Packet success 100%

200 m:
RSSI -70
SNR 8
Packet success 100%

300 m:
RSSI -76
SNR 7
Packet success 98%

400 m:
RSSI -82
SNR 5
Packet success 95%

500 m:
RSSI -88
SNR 2
Packet success 82%

Reliability condition:

packetSuccess >= 90
AND
snr >= 0
AND
rssi >= -90

The furthest distance satisfying the conditions becomes the reliable boundary.

A safety margin is then applied.

Conceptually:

recommendedGroupLimit =
    reliableBoundary *
    (1 - safetyMarginPercent / 100)

Example:

Reliable boundary = 400 m
Safety margin = 20%

Recommended group limit = 320 m

IMPORTANT:

This is currently a SIMULATED link-quality assessment.

It is NOT reading real LoRa RSSI/SNR from the Heltec hardware yet.

This is one of the most important parts of the project.

ml-model/feature_extraction.py

--------------------------------------------------
FALL DETECTION FLOW
--------------------------------------------------

Frontend simulation:

startFallSimulation()

generates simulated IMU samples.

Normal values are generated during normal operation.

A fall-like event is simulated around ticks 4–8.

Example simulated values include increased acceleration and angular velocity.

The generated IMU window is sent using:

communicationService.predictFallFromIMU(windowSamples)

The frontend sends the data to:

POST /api/ml/predict

Python server.py receives the samples.

It then:

1. Extracts features using the existing feature extraction pipeline.
2. Builds the expected 53-feature vector.
3. Runs the trained Random Forest.

Conceptually:

pred_label =
    rf_model.predict(feature_vector)[0]

pred_probs =
    rf_model.predict_proba(feature_vector)[0]

The backend returns the prediction.

So:

Simulated IMU
      ↓
Frontend
      ↓
Python backend
      ↓
Feature extraction
      ↓
53 features
      ↓
Existing Random Forest
      ↓
NORMAL / FALL
      ↓
Emergency workflow

IMPORTANT:

The Random Forest executes in Python backend.

The browser does NOT execute the Python ML model.

--------------------------------------------------
FALL ALERT COUNTDOWN
--------------------------------------------------

When a fall is detected:

A 10-second countdown is shown.

The user gets an opportunity to cancel a false alert.

EmergencyPage.tsx contains:

[I'M OK — CANCEL]

This calls:

cancelFallAlert()

If cancelled:

- countdown is stopped
- simulation intervals are cleared
- fall alert stage becomes cancelled
- SOS is not sent

If the countdown reaches zero:

confirmFallAndSendSOS()

is triggered.

This creates an emergency packet with:

messageType = FALL_DETECTED

and sends it to the group.
